# Modules 16, 17, 19 - Dashboard, dedicated Preview, Template gallery

## Dashboard (doc 16) - `/dashboard`
Navigation overview only: resume/template counts, profile readiness, local save location, three most recent resumes (name, role, date - never document content). No embedded preview or file browser. Pull-to-refresh and refresh on every entry. Admin analytics dashboard is not built yet.

## Preview (doc 17) - `/resumes/:id/preview`
Separate route outside the shell. Fetches `GET /resumes/:id/render-model` (the same model the export uses) and renders it with text bindings only (no `innerHTML`) on real A4/Letter dimensions: zoom +/-, fit width, fit page, page count, dashed page guides, overflow warning above 2 pages, PDF/HTML export, back to editor (editor saves pending edits first). Exact pixel parity with the PDF engine is not guaranteed (doc 17 s.5).

## Template gallery (doc 19) - `/templates`
**Catalogue: all 314 templates** (original families 10/8/8/6/5/5/5/4/4/5 plus four style families Bold & colorful 10, Elegant & editorial 10, Minimal & airy 14, Structured & sidebar 10, plus 21 role- and niche-focused 10-template expansion families: Professional services, Legal & compliance, Finance & accounting, Academia & research, Nonprofit & social impact, Military & veterans, Startup & founders, Product & growth, Data & AI, Marketing & communications, Hospitality & events, Retail & operations, Logistics & supply chain, Real estate & property, Freelance & independent, Career change, Returnship & re-entry, Staff & principal IC, Design studio, Media & entertainment, Wellness & fitness). 3 hand-written seed packages in `template.catalog.ts` + 311 generated from two data tables (`template.families.ts`, `template.expansion.ts`: a family supplies defaults, each row overrides, shared `buildTemplates`). No per-template layout code; renderers interpret declarative tokens: `layout` (single-column | two-column + `sideSections` | timeline), `theme.density` (compact/normal/relaxed: margins, spacing), `theme.headerBand`, `theme.headingStyle` (plain/bar/tint/short), `theme.nameScale`, `headerAlign` (left/center/right), font/size/accent/heading transform/alignment/rule, `sectionOrder`, plus gallery metadata `careerLevels` and `style`. Published versions stay immutable: change a look by shipping `version: 2`.

Gallery: category chips, text search (name/description/tags/category), selects for ATS profile, layout, career level, style and page format (filters combine), result count, empty state + clear, CSS thumbnails driven by the manifest (band, columns, timeline, rules, density), ATS label per card and a parser-reliability warning for every non-ATS-first template (never promises a pass). Every card is a **live thumbnail**: the shared render model filled with a fixed fictional persona (`GET /templates/:id/sample`, built by the same `buildRenderModel` from `templates/sample-profile.ts`, never the caller's profile), fetched lazily when the card scrolls into view (CSS mock only as fallback if the sample fails). Each card has **Preview** (dialog, full-screen on phones, Esc/backdrop closes) showing that template at full size with dummy data and a "sample data only" note; Preview exists for templates only. **Use template** (card or preview dialog) goes straight to Step 3: it creates the user's resume with that template (default name "My resume - <template>") and opens it in the editor, or sends the user to the profile if none exists (409); with `?resumeId=` it switches that resume's template (content untouched).

**Resume flow stepper** (`<app-resume-stepper>`, shown on profile, gallery and editor): 1 Add Profile Details, 2 Choose Template, 3 Edit Template, 4 Export. Completed/reached steps are tappable; on narrow screens it shrinks to numbered dots with only the current label (others stay screen-reader named). Stable tour hooks: `data-tour="resume-stepper"`, `stepper-step-profile|template|edit|export`; primary action buttons carry `step-profile-action` (Continue to templates), `step-template-action` (Use template), `step-edit-action` (Continue to export), `step-export-action` (Download PDF). Ionic keeps previous pages in the DOM, so tours must target the visible one.

Rendering: preview (Angular), PDF (pdfkit), HTML and DOCX all read the shared render model (`layout`, `sideSections`, `theme`). Preview/HTML/PDF render two-column rails, timeline rails and header bands; DOCX stays a single editable flow (header band becomes shaded paragraphs) - a deliberate parser-friendly limitation. ATS rules enforced in tests: ATS-first is always single-column with no band; every accent has >= 4.5:1 contrast on white.

## Visual editor (doc 16 step 3) - `/resumes/:id/design`, component `<app-visual-editor>`
Canva-style editing on the live page. Code: `apps/web/src/app/features/visual-editor/`. Host it with `<app-visual-editor [resume]="r()" (saved)="r.set($event)" />`; call `flush()` to save pending edits before preview/export. Route `resumes/:id/design` hosts it full height.
- **Select / edit**: click a block or text to select (outline + floating toolbar); click again, double-click or Enter edits in place (plain text only, Enter commits, Esc cancels, pasted text is flattened). Enter in a bullet continues with a new bullet; empty bullets are dropped.
- **Reorder**: drag the grip (pointer events: mouse, pen, touch), the up/down buttons, Alt+Arrow, or the Sections outline (also hide/show/delete). Sections reorder inside their column (two-column rails stay put); items reorder inside their section.
- **Add / duplicate / remove**: sections (any standard type or a custom one), items, bullets. Duplicates get new ids and copy formatting. Undo/redo (buttons, Ctrl/Cmd+Z, Shift+Ctrl/Cmd+Z, Ctrl+Y) covers every change; typing-style edits coalesce.
- **Images**: profile photo (header) and logos (items). File picker (PNG/JPEG/WebP/GIF, 8 MB source cap, SVG refused), then a square crop dialog (drag, pinch, wheel, slider, arrow keys), then a small cropped PNG/JPEG data URI (<= 300k chars) saved inside the document; scale in points. The original file never leaves the browser.
- **Formatting per element**: font (3 standard PDF families), size 6-36 pt, bold, italic, colour (theme tokens accent/text/muted that follow the template, an 8-colour palette or custom hex), alignment, space after. Unset = template default; reset button per element.
- **Zoom**: +/-, fit width, fit page, Ctrl/Cmd+wheel and two-finger pinch. **Responsive**: floating toolbar next to the selection on desktop/tablet; bottom sheet below 768 px with 44 px targets; one finger scrolls, two fingers zoom.
- **Autosave and versions**: edits autosave 1.2 s after the last change through `PUT /resumes/:id/draft` (the existing optimistic-concurrency endpoint; a 409 shows a conflict banner and keeps the edits). "Save version" flushes, then creates an immutable version (the snapshot is the render model, so edits, photo and styles are in it).
- **Data model**: a declarative document `Resume.overrides.doc` (no new column or migration): `{ v:1, header:{name,headline,contacts,photo}, sections:[{id,type,title,text?,items?,hidden?}], styles:{ elementKey: {font,sizePt,bold,italic,color,align,spaceAfterPt} } }`. Element keys: `header.name|headline|contacts`, `s.<id>.title|text`, `i.<id>.title|subtitle|meta|text|bullets|tags|url`. Until the first edit the resume still follows the career profile; the first edit snapshots the profile-derived render model into the document. "Reset to career profile content" sends `doc: null` to go back. Header links stay profile-driven.
- **Server**: `sanitizeDoc` (strict allowlist; caps: 20 sections, 60 items, 30 bullets, 24 images, 300k chars per image, http(s) URLs only, PNG/JPEG data URIs only, unknown keys dropped) runs on every write (`mergeOverridesOnWrite`) and every render. `buildRenderModel` applies the document via `applyDoc`, so preview, PDF, HTML, DOCX, versions and match/ATS read the same model. Saves from the classic editor that omit `doc` keep the stored document. JSON body limit is 4 MB so drafts can carry images. No generated bytes are stored: images are part of the resume document, exports stream and are discarded. Tenant + owner checks are unchanged (`ResumesService.owned`).
- **Export parity**: HTML and PDF apply per-element styles (theme tokens resolved to hex, standard PDF faces Helvetica/Times/Courier x bold/italic), draw the photo round-cropped and logos inline; a corrupt image is skipped and never fails the export. DOCX/XLSX use the edited text and structure but ignore styles and images (single editable flow, documented limitation).

## Resume editor screen (step 3/4) - `/resumes/:id`
The page embeds the visual editor (`<app-visual-editor>`, autosaves; flushed before Preview and Continue to export) plus Details. **Sections, Design and Versions live in a panel beside the preview** (sticky side panel from 768 px; bottom sheet opened by the Customize button below that, with backdrop, close button and the action bar hidden while open). **Continue to export** saves pending edits, then switches to Step 4 (`?step=export`): one-tap **Download PDF** with defaults - no options dialog and no extra details (`ExportService` no longer shows the first-run alert; the first web export silently uses a plain download). Advanced options remain after the first export: HTML/DOCX/XLSX buttons, a Save location link to Files (choose a folder there), and the full-page Preview route.

## Known gaps
Visual editor: no free-form (x/y) positioning or multi-select; fonts limited to the three PDF standard families; DOCX/XLSX ignore styles and images; the visual-editor sheet (`ve-sheet`) still mirrors the page markup rather than using `<app-resume-sheet>`; items cannot be dragged between sections; once a document exists, career-profile edits no longer flow into that resume until reset; the editor component itself is covered by Playwright, Jest covers the logic.

Server-side page-break diagnostics, glyph checks, "final export preview" using the real PDF, per-template thumbnail images and visual-regression snapshots, DOCX multi-column, language/script filter (PDF uses standard Latin fonts only). Gallery filter labels and some legacy editor strings are still English literals (new flow strings are i18n keys); Android hardware back does not close the template preview dialog.
